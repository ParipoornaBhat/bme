01 The dataset

Knee MRI from three scanners across two vendors. Collected, de-identified, converted and indexed.

PropertyValue
Cases107 usable — 47 BME, 60 non-BME (1 archive unreadable)
RegionKnee throughout — no mixed-joint problem
ScannersUIH uMR 780, Siemens Avanto, Siemens Symphony
Edema sequenceFat-suppressed PD/T2/STIR — present on 107 / 107
T1 sequenceOnly 18 / 107, and just 5 of 47 BME cases
Storage3.0 GB source → 5.7 GB generated

The finding that changed the model. The original plan used T1 as a second input channel, to tell real edema apart from lookalikes like red marrow and cysts. Only 16% of cases have one — and just 5 of 47 positives.

So the model is single-channel, and specificity has to come from elsewhere: a left–right mirrored copy (asymmetry is the earliest sign of edema) and an anomaly residual from a model trained only on healthy marrow. Neither needs a second scan.

Patient data

Every filename is pseudonymous. 108 archives and 121 images renamed to BME-001.zip / BME-2D-004.jpeg; PHI stripped from 13,818 DICOM headers. No patient name exists anywhere on disk except three mapping files, which are gitignored and never leave the local machine. Nothing patient-identifying is in the repository or the cloud database.

02 How the model works

Two stages, in sequence. This is the single most important design decision in the project.

Because Stage C only ever looks inside Stage B's mask, mistaking muscle or joint fluid for edema is structurally impossible rather than something the network has to learn. It also solves the human problem: the computer outlines the bone, so a non-radiologist annotator only has to judge whether marrow looks brighter than it should.

U-Net and CNN are not alternatives. Everything here is a CNN — that is the family, not a specific model. ResNet and MobileNet are classifiers ("is there edema?"). U-Net is a segmenter ("where exactly?"). Different jobs, so different models. The 3D system is nnU-Net, a self-configuring U-Net.

Working as a team of four

The imaging never moves through the app — it is patient data, shared by hand. The database holds the ledger: who annotated which case, when, and how large the segments were.

  • Saving records you as the annotator.
  • A case someone else finished, with no local file, raises an amber “your local copy is behind” banner naming who to ask.
  • Several people can annotate the same case. Each save writes a canonical file and a per-annotator copy — otherwise the last person to save would erase everyone before them, and inter-rater agreement could never be measured.
  • Work is pre-assigned: ~26 cases each, the good thin-slice cases spread evenly, and 5 cases deliberately shared by all four.

Pipeline scripts

Twelve scripts cover header inspection, de-identification, stable case IDs, renaming, DICOM→NIfTI conversion, 2D slice extraction, 2D training, annotation validation, nnU-Net dataset building, and 3D training. Every script that writes has a dry-run and refuses to overwrite without --force.

05 Results

2D classifier, five folds, split by patient so no case appears in both training and validation.

MetricCase levelReading
Accuracy64.5%
F10.587
ROC AUC0.6650.5 would be random guessing

This is weak, and worth presenting honestly. Two reasons, both diagnosed:

Noisy labels. The label is per case, applied to every slice. A BME patient's scan contains many slices with no edema visible, and all of them are labelled BME. Part of the task is genuinely unlearnable.

Overfitting. Training loss fell from 0.51 to 0.03 over six epochs while validation accuracy stayed near 60% — it stopped learning the disease around epoch three and started memorising. Three to four epochs should score better.

A weak baseline you can explain defends better than a strong number you cannot. It is also precisely the argument for the 3D system: voxel-level annotation removes the label noise.

3D segmentation

No results. Zero annotations, so it has never trained. The pipeline is written and verified against real 3D Slicer output — geometry, splits and leakage checks all pass — it is only waiting on labelled cases.

Realistic targets

MetricTarget
Bone segmentation Dice0.92
BME lesion Dice0.60 – 0.72
Lesion sensitivity0.80 at ≤1.5 FP/case
Case-level AUC0.90

Published fully-automated BME work reports sensitivity of 0.58–0.83 on larger datasets. Dice 0.62 with sensitivity 0.80 is a publishable result. Chasing 0.90 on lesions at this data scale would indicate a leak, not a good model.

06 What happens next

In order. Each step feeds the one after it.

  1. Re-run ResNet-18 properly — five folds, three to four epochs. The app currently shows a throwaway MobileNet smoke test, not a real result.
  2. Annotate 10 cases in the browser. The critical path. Everything else waits on this.
  3. Measure inter-rater agreement on the 5 shared cases. That number is the model's realistic ceiling and makes every later result interpretable.
  4. Train Stage B — bone segmentation. Should clear Dice 0.90 easily. If it does not, the data pipeline is broken, not the model.
  5. Train Stage C — edema, then add the mirror and anomaly channels as an ablation.
  6. Quantification — lesion volume in mm³ and a 3D surface.
  7. Explainability — uncertainty maps and a per-lesion evidence table.

Ask the guide now — these have lead time.
