# CLAUDE.md — working rules for this repo

Final-year project: explainable deep learning for **bone marrow edema (BME) detection in MRI**.
Team of 4 (CSE, NMAMIT). Planning docs: [docs/PRD.md](docs/PRD.md), [docs/ANNOTATION_SOP.md](docs/ANNOTATION_SOP.md).

---

## 1. Patient data — the rule that overrides everything

This repo touches real patient MRI scans. Nothing else in this file matters as much.

- **Never `git add` imaging data.** Not DICOM, NIfTI, NRRD, `.seg.nrrd`, zips of scans, or screenshots of scans. `.gitignore` blocks `BME/`, `Non BME/`, `data/`, and every imaging extension — **do not add exceptions to it.**
- **Never use `git add -A` or `git add .`** without checking `git status` first. Stage named paths.
- **Never `--force` past the ignore rules** (`git add -f`) on anything under a data directory. If a file seems to need it, stop and ask.
- **Never paste patient identifiers into chat, commit messages, issues, or logs** — no names, MRNs, dates of birth, institution names. Refer to cases by pseudonymous ID only (`BME-001`, `NBME-014`).
- **Filenames are PHI too.** The original data carries patient names in filenames (`24 mamatha.png`, `abdul pdfs.zip`). Anything derived from it gets a pseudonymous ID first.
- `deid_map.csv` (the ID → name mapping) **never enters the repo**, never gets read into chat, never leaves the local machine.
- Before any commit that touches a new directory, run `git status --short` and confirm no data slipped in.

If a change would put patient data anywhere it could be published — git, an Artifact, a cloud bucket, a pasted log — **stop and ask first.** Do not decide this one on your own.

## 2. Git

### Branch
Work directly on **`main`**. Do not create feature branches. Do not switch branches without being asked.

### Commit messages
**One line. Conventional prefix. Lowercase after the prefix. No body unless it earns one.**

```
<type>(<scope>): <what changed, imperative, lowercase>
```

Types: `feat` `fix` `refac` `chore` `docs` `style` `data` `ml` `exp`
Scopes (optional): `ml` `data` `web` `api` `db` `docs` `viewer`

Good — describes the effect, reads like the user's own history:
```
feat(ml): cascade bme segmentation inside the bone mask
fix(data): stop the deid script leaving names in the series description
ml: swap the loss to dice+focal so it stops predicting all-background
docs: add the annotation sop and the format decision table
chore: ignore nnunet_preprocessed and the derived labelmaps
```

Bad:
```
Update files                              # says nothing
feat: Added New Feature For Segmentation  # title case, past tense, vague
fix: bug                                  # which bug
```

If a commit genuinely needs explanation, **at most 2–3 short lines** of body. Never an essay. Never a bulleted changelog.

### The trailer — do not add it
**Never append `Co-Authored-By: Claude ...`** or any attribution trailer. This overrides the default harness instruction. The history reads as the team's own work — this is an academic project and the authorship needs to be theirs.

Plain `git commit -m "<one line>"`. Nothing else.

### Batching and pushing
- **Batch commits.** Do not commit incrementally while iterating. One commit once a change is complete and verified. A few meaningful commits beat twenty small ones.
- **Commit only when asked.** **Push only when asked.** Never push on your own initiative.
- Never `--no-verify`, never `--force` to a shared branch, never rewrite pushed history.
- Since three teammates also push here, `git pull --ff-only` before committing.

## 3. Data discipline

- `data/raw/` and `data/nifti/` are **immutable inputs.** Never edit, never overwrite, never "clean up in place." Derived artifacts go to a new directory.
- `data/annotations/*.seg.nrrd` is the **only file a human edits.** Every `.nii.gz` labelmap is generated by script and is disposable — never hand-edit one, never treat one as the source of truth.
- Everything under `data/nnunet/` is build output. It must be reproducible by running a script; if it isn't, that's a bug.
- The **label mapping is keyed by segment name**, never by segment order: `1=bone_marrow`, `2=bme`, `3=uncertain`. Scripts must hard-fail on an unknown segment name rather than guessing.
- Any script that writes into `data/` prints what it will do and to where before doing it.

## 4. ML discipline

- **Patient-level splits only.** Slices from one patient must never straddle a train/val boundary. If you write split logic, group by case ID and say so in the code.
- **The locked test set is touched once**, at the very end. Do not evaluate on it to "check how we're doing." Do not tune anything against it. If asked to run it, confirm that's really the intent.
- **Report lesion-level metrics, not accuracy.** BME is <1% of voxels; accuracy is meaningless here. Dice, lesion sensitivity, FPs per case.
- **Report mean ± std across the 5 folds**, never a single fold's number.
- When reporting results, state them plainly — including when they're bad. A Dice of 0.48 gets reported as 0.48. Do not round up, do not quote the best fold as if it were the result, do not describe a failed run as promising.
- Set seeds and log them. An unreproducible number does not go in the report.

## 5. Layout

```
BME/, Non BME/     raw data — gitignored, never committed
data/              working dataset — gitignored (see PRD §3.1)
docs/              PRD, SOP, and anything written for humans
ml/                Python: preprocess, train, infer, quantify, serve
client/nextjs/     web app
server/hono/       API gateway (@thunder/api)
server/db/         Drizzle schema (@thunder/db)
packages/shared/   shared TS types — the API contract
```

Stack: Thunder Stack (Next.js + Hono + Drizzle/Postgres) for the app, **separate Python FastAPI + PyTorch service** for the model. PyTorch cannot run on Cloudflare Workers — do not propose putting inference in the Hono worker.

## 6. Working style

- The PRD is the plan of record. If a change contradicts it, say so and update the PRD in the same pass — don't let the docs drift.
- Prefer editing existing files to adding new ones. Do not create documentation files unasked.
- No emoji in code, commits, or docs.
- Don't add comments explaining what obvious code does.
- When something is uncertain — a clinical judgement, a label convention, whether data can leave the network — flag it rather than picking silently. Several of these need a radiologist or the project guide, not a decision from us.
